### Known tooling limitation: new Swift files are unreliable in this project

**Do not create new Swift files in this project without reading this first.** During the flashcard/deck feature build, every attempt to add a brand-new `.swift` file failed in one of three ways:
1. A file written via the MCP bridge's file-write tool compiled as a **bundle resource** (`Copy X.swift` in the build log) instead of Swift source — present in the navigator, but not in the module.
2. Deleting that file via Xcode's UI ("Move to Trash") and recreating it via Xcode's own File > New File *did* fix it for the rest of that Xcode session (confirmed via a successful build).
3. ...but after fully closing and reopening Xcode, the recreated file vanished from the project model entirely (`XcodeRead` returned "file not found in project structure"), and `grep`-ing `project.pbxproj` showed it had **zero trace** there — whatever fixed it in (2) was never actually persisted.

Root cause, as far as this session could tell: the project has two different things both named "StudyRPG" pointing at the same on-disk folder — a `PBXFileSystemSynchronizedRootGroup` (modern, auto-membership) *and* a conventional `PBXGroup` with hand-wired `PBXFileReference`/`PBXBuildFile` entries for the original handful of files (`GameContent.swift`, `ContentLoader.swift`, `ContentView.swift`, `MyApp.swift`, the `Content/*.json`, `Assets.xcassets`) — likely added by an earlier session as a workaround for the scheme-resolution problem mentioned further down. Files explicitly wired the second way build reliably, every time, across restarts. Files relying on the synchronized group's automatic inference do not, in this project.

**The fix that was used**: don't create new Swift files at all. Put new code into the four files that are explicitly wired in (`GameContent.swift` for models, `ContentLoader.swift` for services, `ContentView.swift` for views, `MyApp.swift` for app wiring), with `// MARK:` sections and doc comments pointing back to the relevant game.md section. This is why those four files are larger than normal for their content.

**What was tried and ruled out**: the Target Membership checkbox/pencil-icon dialog in the File Inspector (only controls platform scoping, not Sources-vs-Resources); `UpdateFileCompilerFlags`/`GetFileCompilerFlags` (can inspect/set flags on an existing Sources member but can't add one); asking the user to toggle things in Xcode's UI repeatedly (burned a lot of a frustrated user's patience for no result). Editing `project.pbxproj` directly was attempted once and blocked by a safety check — don't try it; it's genuinely unsafe while Xcode has the project open, and there's no tool in this environment that edits file/build-phase membership for a synchronized group's files.

**If you need to add new files in a future session**: first try it as a quick experiment (create one trivial new file, build, close/reopen Xcode, build again) before committing a feature's worth of code to it. If it's still broken, keep using the four-file pattern above, or ask the user whether they're willing to manually reconcile the duplicate "StudyRPG" groups in Xcode's UI (would need investigation into which one to remove — not attempted this session).

As of 2026-10-17 this no longer reproduces — `BuildProject`, `RunProject`, and `DeviceInteraction*` all work normally against the `StudyRPG` scheme/target. ## Decisions list as worded before 2026-10-18 condensation

- Flashcards: one question, one correct answer, any number of optional author-written wrong answers. Question/answer/wrong-answer may carry an image. Missing wrong-answer slots are filled from other cards in the same deck at presentation time, and the correct answer is sometimes withheld ("None of these") so elimination alone can't win — see game.md §4 for the exact rules. Decks are authored in-app (deck editor), not imported from external files, for now.
- Cards track their own accuracy (not just decks) — see game.md §4.2. Deck accuracy is derived (sum correct ÷ sum attempts across the deck's cards), not an average of card rates.
- Every answer is logged permanently (not just aggregated into correct/total) so future features can be built from history already being collected — see game.md §4.2. This is intentional over-collection for a reason; don't remove fields from `AnswerEvent` without checking whether a planned future feature (§16) needs them.
- Any number of decks can be active for a run; they're pooled into one shared question source for both heroes. Cards you get wrong are weighted to reappear more often (see game.md for the weight formula).
- Fights can have 1–3 enemies. You tap a skill, then tap an enemy (bouncing arrows mark valid targets). Each enemy has its own independent "charge" counter that ticks every hero turn (right or wrong) and fires that enemy's scheduled move at its threshold.
- A wrong flashcard answer makes the skill **fizzle** and the **single strongest** living, un-stunned enemy hit the answering hero once, rolling at most `combat.wrongAnswerMaxDice` (1) of its dice (user decision 2026-10-18, replacing "every enemy hits both heroes"). It does **not** reset charge counters, and charges still tick every hero turn right or wrong.
- Scheduled enemy attacks always hit both heroes, rolling separately for each (user decision 2026-10-18). In Fast mode those rolls are thrown as one batch but still applied one after another.
- Heroes learn skills: after every won fight/elite, one hero (alternating) picks 1 of 3 unknown class skills or skips; at most 4 equipped (`skills.maxEquipped`), any number known; loadout editable anywhere outside fights, with a campfire shortcut (user decision 2026-10-18).
- Gear is per hero: 3 slots (weapon/armor/trinket), effects only on the wearer; drops from fights/elites/shop/events. Potions stay a shared bag (user decision 2026-10-18).
- Settings exist (Fast mode, pause after wrong answers, pause after right answers — off by default, so a right answer moves on immediately — haptics) — presentation only, stored in UserDefaults, never balance.
- Physical vs magic damage (user decision 2026-10-18): magic ignores all block and armor; Wizard damage skills, the Bog Witch's attacks and boss `fire` are magic (game.md §7.4).
- Map (user decision 2026-10-18): no shop/campfire at the start, every route passes a shop or campfire, and the row before the boss is all campfires (game.md §9).
- No visible navigation bars on any screen — only their buttons (user request 2026-10-18).
- Long-term plan (not built): 3 acts per run with their own themes and bosses, boss relic choices, ascension up to ~20 levels (game.md §16).
- Also planned (not built): a Glossary (all skills/potions/gear/relics, revealed as encountered) and a Bestiary (all monsters with stats and skills, unlocked as encountered), plus rule-driven monster skills (game.md §16.1).
- Combat is strictly sequential — never let two actions/animations overlap (game.md §7.6). Prefer symbols + semantic colors over text on the fight screen.
- Using a potion/consumable is free: no flashcard, no turn cost. Skills/spells always require a correct flashcard answer first.
- All damage/healing/other random numbers are produced by the physically-animated 3D SceneKit d6 dice (`Dice3DView`, count + flat modifier), not abstract RNG with no visual. The user confirmed the 3D dice on 2026-10-18 (the old 2D dice code was deleted).
- One run = one map (left-to-right scrolling, branching nodes) ending in one boss fight. Permadeath: losing resets gold/items/relics/HP. The only thing that survives a loss is flashcard accuracy history.
- Target difficulty: the game should still be meaningfully hard even assuming the player answers every flashcard correctly. Don't balance around the player getting some wrong.
